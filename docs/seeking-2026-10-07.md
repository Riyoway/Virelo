# Seeking during compatible/adaptive playback

The progressive HLS encoder publishes only generated segments. A film can be two hours long while its current browser `seekable` range ends after a few minutes. Assigning an unencoded target to `currentTime` allowed HLS/browser processing to return playback to the generated edge.

The npm player now distinguishes direct/buffered seeks from requests outside the currently generated HLS window. Direct playback still uses native byte-range seeking, with no encoder request. An out-of-window compatible or adaptive seek asks FFmpeg to start at the requested position instead of waiting for conversion from minute zero.

Window caches have separate paths and job keys. The status API includes the actual window start and absolute coverage. Window playlists mark their unencoded prefix with standard `EXT-X-GAP` entries, preserving absolute movie timestamps for existing captions, queues and progress. A complete original cache is reused when it already covers the request. Arbitrary forward/backward seeks create a new window only when needed. Window starts decode rather than stream-copy preroll so video/audio have the same origin.

React event handlers own the seek intent. The latest target remains visible while obsolete time updates are ignored; rapid dragging is debounced and request tokens cancel stale handoffs. Playback/pause intent, manual quality ceilings and the full movie duration survive the handoff. Network Auto is not enabled locally.

References: [MDN seekable](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/seekable), [HLS.js API](https://github.com/video-dev/hls.js/blob/master/docs/API.md). Browser verification uses the installed HLS.js/Chromium versions, not assumptions about current library behavior.

## Verification

`tests/playback-seek.test.mjs` covers ordinary/native seeking, unencoded coverage, backward gaps, absolute playlist timestamps and invalid inputs. `tests/transcode.test.mjs` includes separate absolute seek-cache coverage.

`scripts/audit-seeking.mjs` uses only synthetic videos and isolated temporary storage. It freezes initial HLS playlists at twelve seconds, then exercises real FFmpeg/HLS seeks into the later portion of the file. Set `VIRELO_EXPECT_SEEK_FAILURE=1` against the previous frontend build to reproduce the bug; omit it for the fixed build. Optional `VIRELO_SEEK_ASSETS` reuses the generated synthetic fixtures. Set `VIRELO_SEEK_LONG=1` to include a real synthetic 1:57:21 clip and seek to 47:24.4, then back to 14:56.2 while paused. Set `VIRELO_TEST_NODE_PACKAGE`, `VIRELO_TEST_CHROMIUM`, and optionally `FFMPEG_PATH` to the installed tools.

Verified results (2026-10-07): the old production frontend reproduced the snap back from 92.4 seconds to the 12.032-second generated edge. The fixed production build passed all 18 FFmpeg/Chromium assertions, including compatible audio, rapid seeks, forward/backward windows, pause intent, manual 360p ceilings, direct-file seeking without an encoder request, full-length slider duration, and the 47-minute feature-length case. `npm test` passed 67/67 tests; server/web builds, web typecheck, `npm run pack:check` dry run and `git diff --check` passed. The actual user film was not opened or changed.

No user library, cache or running server is restarted by this audit. Server and frontend builds must both be updated; a server already running old modules needs a normal restart before using the new seek API. No npm publication, version bump, commit or push is included.
